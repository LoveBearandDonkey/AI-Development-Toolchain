msModeling 端到端用法

以下流程依据当前 msmodeling 仓库的 CLI、配置模板和使用指南，以昇腾大模型在线推理为例。先选用或定义设备画像，再按需仿真筛选部署配置。有实机时可用 OptiX 寻优并复测。

  • 期望值性能目标、计划负载和搜索范围
  • 实际值已知规格、代码、已选配置和实测记录
  • 仿真结果仿真估算和据此筛出的候选配置
第一步的任务记录与参考资料

模型和目标先由用户记在本地任务记录中，可以用 IDE 编辑 Markdown。执行单点或吞吐仿真时，再把适用的值填入仓库 Web UI 或 CLI。比如吞吐仿真用 --input-length、--output-length 提交长度，用 --ttft-limit、--tpot-limit 提交时延目标。

--help 显示所选命令的用法、参数名、哪些参数必填，以及已注明的取值和默认值。例：python -m cli.inference.throughput_optimizer --help。

支持矩阵列出仓库支持的模型系列和版本，以及各仿真模块支持的功能，例如量化、并行和 PD 分离。用它核对本次模型和计划使用的功能。模型与特性支持矩阵

自定义画像文件和 --device 怎么配合

已有画像可直接记录其注册名，内置画像查 tensor_cast/device.py。需要自定义时，可以在自己的工作区用 IDE 编写并维护 my_device.py，在 DeviceProfile 中定义算力、显存和互连。

运行前，把这份文件的副本放到本次仿真实际使用的 tensor_cast/device_profiles/ 包目录。新进程会从该目录导入文件，并用定义里的 name 注册画像。例如，定义写的是 name="MY_DEVICE"，CLI 就传 --device MY_DEVICE。设备数量另用 --num-devices 传入。

用 TEST_DEVICE 跑通两种仿真

按安装指南配置环境后，在 msmodeling 仓库根目录运行。示例需要能读取 Qwen3-32B 的模型配置，吞吐示例只设置了 TPOT 上限。

python -m cli.inference.text_generate Qwen/Qwen3-32B --num-queries 2 --query-length 3500 --device TEST_DEVICE
python -m cli.inference.throughput_optimizer Qwen/Qwen3-32B --device TEST_DEVICE --num-devices 8 --input-length 3500 --output-length 1500 --quantize-linear-action W8A8_DYNAMIC --quantize-attention-action disabled --tpot-limit 50

也可以运行 python web_ui/main.py，在 http://127.0.0.1:5173 打开仓库自带的 Web UI，配置并查看上述仿真结果。

Agent 化的 msModeling 使用体验

当用户在 Codex 客户端或 VS Code 里发起任务，最显著的变化是交互单位从「配置一次工具」变成「完成一个性能判断」。Agent 可以读工作区、组织参数和调用工具。用户需要随时看清它用了什么条件、为何推荐某个方案，以及结论能用到哪里。以下是端到端体验设计提议。

用户从一句问题开始

「用当前工作区的 Qwen3-32B 配置，比一比两套 A3 部署方案。以现有业务负载为准，TTFT 上限 1.5 秒、TPOT 上限 50 ms。先仿真，给我最值得上机验证的方案。」

Agent 先给可编辑的任务卡

列出已识别的模型与版本、两套画像与设备数、负载来源、指标口径和执行范围。缺少业务负载或卡数口径时，定位具体缺项并请用户补充。

一张任务卡贯穿仿真与复测

发起与确认 · 任务卡

首屏可见
用户目标、已识别输入、关键缺项、默认值及其来源。本次是只仿真、复用历史实测，还是允许上机。
用户能做
直接修正输入。需要上机时，确认机器、时间或次数预算及允许改动的范围。

运行中 · 进度与阻塞

首屏可见
当前在测什么、为什么测、已用了多少预算、是否在等用户。失败时给出失败环节、证据和可选动作。
按需展开
生效命令、配置差异、每轮候选、原始日志和 Trace。通过运行 ID 恢复到最近的可用结果。

收尾 · 候选对比与决策包

首屏可见
基线、推荐方案、一个备选及淘汰原因。每项指标标注目标、数值、单位和来源，并给出「仿真达标」「实测达标」「未达标」或「证据不足」。
用户能做
展开同负载复测证据，导出部署配置，或带着当前任务继续补证据和比较另一组方案。

用户会少做什么，又需要多看到什么

环节退到后台的操作需要强化的输出或视图
模型与画像在多个表单重填模型路径、卡数、画像注册名和同一份业务约束。任务卡突出输入来源、卡／die 口径、缺失字段。已有画像直接引用，自定义规格保留可审阅的 DeviceProfile 源码。
仿真与筛选记 CLI 参数、切换仿真入口、手抄候选指标、自己判断该补哪种仿真。候选表解释每个方案解决什么问题、触及哪条约束、为什么淘汰。保留实际生效的配置和链接可打开的结果。
寻优与复测重复改配置、启动压测、翻日志、整理每轮记录。只提示需要用户决定的预算、资源和变更。展示基线与推荐方案的同负载复测、运行记录、测量口径及待补证据。
交接与回看从聊天、终端和目录里重新拼一份报告。使用同一运行 ID 找到简报、机器可读结果、配置和原始证据。区分期望值、实际规格、仿真结果与实测，演示数据单独标明。

msModeling 的体验怎么调整

  1. 先让 Agent 能稳定调用。 提供可查询的参数和能力约束、执行前校验，以及结构化结果和错误原因。保留可复现的 CLI 与配置。沿用 OptiX 已有的候选、进度、结果文件约定，逐步补齐仿真和实测之间的交接字段，例如任务 ID、运行 ID、配置版本与证据来源。
  2. 把对话做成任务入口。 在客户端或 IDE 内读取用户指定的工作区材料，显示可编辑的任务卡。按需展开传统表单。更换画像、负载或软件版本后，标明哪些对比需要重跑，保留同条件下仍可使用的结果。
  3. 把 Web UI 做成工作记录与结果视图。 从对话直接打开某次运行、候选或证据。图表和表格帮助用户判优，当前状态提供对应动作，例如「确认上机」「看失败原因」「导出部署配置」。同一份运行记录也能在 IDE 打开配置、CSV 和 Trace。
