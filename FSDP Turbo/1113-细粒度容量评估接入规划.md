# 细粒度容量评估接入规划

目标是复用既有配置解析与Rank内存表达，将配置、模型结构、后端执行语义和细粒度内存策略接到同一个容量模型。第一层先支持手动占用账的容量叠加；第二层再用真实配置与版本化模型替代手动假设。用户关注的验收顺序仍是“先放得下，再挑最优，尽量免跑”。

## 第一层交付与边界

[激活生命周期Demo](重计算与Swap-激活生命周期.html)新增“容量叠加”抽屉分组，输入本作业可用设备容量、非激活常驻占用、安全余量，以及可重叠的临时占用事件。每个事件具有名称、起点、终点、大小和适用候选；起点计入、终点释放。事件可以覆盖前向、反向、更新阶段，或只影响一个候选。

默认显示设备总内存，保留激活视图切换。三个候选分别计算峰值、峰值时刻、最小余量、首个超预算时刻及超预算区间。隐藏曲线只改变显示，不改变判定；点击抽屉中的超限定位按钮，时间轴与上方张量图一起跳转。

计算关系为：

- 总内存(t)＝激活(t)＋非激活常驻占用＋该时刻生效的临时事件。
- 设备预算＝本作业可用容量−安全余量。安全余量不算实际占用。
- 激活视图的虚线＝设备预算−非激活占用(t)。候选临时事件不同，分别显示同色预算线。
- 总内存超过可用容量为“超容量”；仅超过扣除余量后的预算为“余量不足”。低于预算且占用账仍缺项时为“信息不足”；假设已列齐时为“假设下可容纳”。

默认教学样例采用40u可用容量、20u非激活常驻占用、2u余量，无临时事件。保留方案总峰值56u，重算和交换均为31u；这些数值仅检验叠加逻辑，不对应真实GB。反向临时峰值和更新时才超限两个预设，用来说明激活下降不保证整个step安全。参数、梯度、优化器状态及运行时底座在此阶段由用户合并输入；临时事件仅填尚未计入的增量，禁止把同一块存储或同一个预留池重复相加。

当前模拟固定为单rank、单micro-batch的一次逻辑step，初始化、加载、首次优化器状态建立、checkpoint保存等阶段未覆盖。抽屉中Rank与micro-batch实例仍是接口意图；输入这些字段不会将结果升级为多rank估计。当前没有接入配置解析器、没有调用V2 MCP，也没有真实训练结果。

## 配置解析器的复用范围

入口为[配置关系平面](../mindspeed-config-mcp/apps/web/config-relation-plane-baseline/training-run-twin-standalone/config-relation-plane-mindspeed-config-mcp.html)。其脚本链包含本地导入、结构与并行校验、容量估算及展示，适合作为第二层入口。

| 现有资产 | 已确认的能力 | 复用方式与补齐项 |
|---|---|---|
| `config-relation-import.js`的`croImport.parseAny/analyze` | 识别JSON、YAML和Shell；输出`flat/partial/mapped/ignored/gaps/structural/unknown/counts` | 保留原始来源、未映射键及缺口，形成共享的规范化输入。YAML是现有解析器支持的子集，Shell只静态解析，不执行命令；增加后端版本及覆盖测试 |
| `MAP/DERIVED` | 映射层数、hidden、heads、KV heads、FFN、DP/TP/PP/CP/EP、序列长度、micro-batch、MoE等 | 沿用字段映射和来源键；对批次语义、默认值、派生值保持明确区分。不要将ETP二档等简化表达当作完整后端参数 |
| `config-relation-observer.js`的`validate`及导入配平 | 检查整除、拓扑等约束，并支持导入后配置调整 | 原始配置、规范化配置、页面配平后的候选分别保留。容量评估不得静默替换用户配置；任何修正都生成可审阅差异 |
| `cro:change/cro:select`、`croObserver` | 传递拓扑更新和选中关系 | 以事件适配层传递到统一输入，不把Demo直接绑定原页面DOM |
| `config-relation-capacity.js`的`croCapacityModel` | 分Stage拆权重，考虑分片、可训练参数、在途微批及运行时开销 | 复用结构拆分与口径说明；将经验系数和支持组合显式列为模型假设，并通过后端适配器确认。静态容量估算不等同于完整生命周期预测 |

所给HTML引用的导入链使用本地`croImport.analyze`等方法，不能因为文件名含mcp就宣称V2 MCP已经调用。后续如接入`parse_training_config`，必须记录真实调用的`mcp_invocation`及返回结果；本地解析、校验、估算与远端分析分别标记来源。

### 五组信息的覆盖判断

| 输入组 | 现有配置页加本Demo | 第二层仍需补齐 |
|---|---|---|
| 模型结构 | 常见Transformer与MoE结构字段已有映射 | 模块树、真实参数形状、共享参数、特殊Attention、实际算子保存点与自定义modeling |
| 训练负载 | 序列、微批、梯度累积、部分训练开关已有入口 | dtype逐对象语义、优化器精确状态、动态/packed形状、损失头、训练阶段和调度方式 |
| 并行映射 | DP/TP/PP/CP/EP/VPP等已有关系与约束 | 后端真实mesh、FSDP/专家分片、复制、各rank非均匀持有及执行顺序 |
| 内存策略 | 本Demo已有范围、对象、缓存、交换、比例、预取和约束控件 | 将字段绑定到后端版本与具体执行对象；方法/算子字段要验证存在且实际被调用 |
| 后端与设备 | 有资源选择和容量展示，本Demo有接口说明 | 精确后端版本、设备可用容量、allocator与通信配置、算子实现及workspace依据 |

因此，两者可以共同承担大部分输入组织和交互，但不能仅因“五组都有表单”就认为容量模型已完整。

## Rank内存示意的复用范围

来源为[Rank的设计表达](../compute-graph-viewer-wzh/Profiling_Insight_and_Tool/rank-intro/rank-intro.html)的“8·内存”。

- `activationScene/activationVolumeHTML/mountActivationVolume`表达当前rank的输入张量、CP序列切分、TP隐藏维切分及EP路由归属，可复用为“这个张量为什么在这张卡上”的解释视图。
- `updateActivationCycle/currentMemoryMicrobatch`表达前向写入、反向消费、在途微批与选中rank，可复用为容量曲线的对象钻取与生命周期联动。
- `memAt/observedFrame`区分张量占用、延迟释放、缓存预留和进程其他占用，可复用其分层解释。Allocated、Activated、Reserved、APP Reserved是嵌套口径，不能相加。

原实现明确提示：立方体画当前层输入切分，未包含本层产生的全部激活，体积不代表GB；上方激活数值是跨层在途汇总。`memOf`中还包含`loadSeed`生成的教学系数，事故模式也有场景化增量。它们可作为教学或回归场景，不能进入真实容量预测而不标记来源。

第二层应给这些视图喂入同一份预测事件与张量清单。不要另建一个只控制动画的时钟，也不要继续用独立的随机系数生成“精确”曲线。可优先抽取场景构造与组件适配接口，保留现有页面，避免整体复制636KB级页面及其上下文依赖。

## 第二层的输入与结果契约

建议采用版本化的`TrainingCapacityCase`，至少分为：

| 部分 | 需要保留的信息 |
|---|---|
| 原始输入 | 文件内容/指纹、来源路径、方言、解析器版本、原始键值 |
| 规范化配置 | 模型、训练、并行、内存策略、后端和设备；每个字段附来源键、显式/派生/默认状态 |
| 分析覆盖 | 已解析、已映射、已参与容量建模、未支持、未知；三种“已完成”分别计数 |
| 模型对象 | 参数/激活/workspace/通信缓冲的shape、dtype、storage别名、字节数、所属rank |
| 生命周期事件 | 对象ID、rank、micro-batch、层/模块/算子、分配/释放/重算/换出/预取/等待、依赖边 |
| 容量与边界 | 各rank可用容量、其他进程占用、安全余量、主机/远端预算、覆盖的执行阶段 |
| 依据与不确定性 | 源码推导、数学推导、历史校准、人工假设；适用版本、误差范围和未建模开销 |

结果按候选、rank和阶段输出内存分量时间序列、峰值与时刻、首个不可满足的分配请求、占用对象清单、余量及适用范围。除总量上限外，allocator模型还需判断“已有占用＋本次申请”是否可满足，解释总量尚未越线却分配失败的情况。

结果状态分为配置不合法、容量超限、容量余量不足、信息不足、在已覆盖范围内预计可容纳。第一层的“假设下可容纳”不得自动映射成“预测通过”。

## 接入步骤与验收

| 步骤 | 交付 | 验收重点 |
|---|---|---|
| 配置入口适配 | 复用`croImport`，统一输入及覆盖报告 | 不丢原始键；不执行Shell；未知字段不自动填零；配平改动可审阅 |
| 两后端语义适配 | Megatron及FSDPTurbo分别绑定版本、模型和能力 | full/selective、分片与交换语义独立；无法映射时明确缺口，不强行共用配置 |
| 张量与事件生成 | 从shape、dtype、实际分片和调度生成事件 | 共享存储去重；checkpoint输入保留；搬运完成前不释放；补算等待输入；预取增加驻留 |
| 生命周期容量计算 | 多rank、多微批、多阶段峰值 | 最坏rank与Stage不能被平均值掩盖；统计同一时刻各项之和；缓存预留不重复计数 |
| 视图适配 | 原配置页负责输入与关系，Rank页负责归属，本Demo负责策略比较 | 所有视图使用同一对象ID与事件；点击超限点能回溯配置、源码依据和仍存活的对象 |
| 免跑评估验证 | 数学可核对样例、历史运行样例、保留验证集 | 报告峰值误差、漏报OOM与误报风险；校准按设备/版本/形状范围绑定，不泛化成无条件精确 |

第二层先从一个具体稠密模型、固定shape与单后端可解释路径建立完整闭环，再扩展MoE、动态shape、并行组合和另一后端；其余场景保持“信息不足”。逐步扩展不能通过隐藏缺口来换取全覆盖界面。

## 免跑且精确对Demo的启示

用户原声同时强调精准、有限集群资源、估算与实跑的gap，以及尽可能通过对话使用工具。Demo应优先帮助判断和追溯，动画承担解释，不作为可信度来源。

1. 入口先给出配置来源、硬件约束和待补信息，再呈现候选结果。AI可根据新证据生成映射或适配，但计算、验证和依据必须可重复，不以自然语言判断替代内存账。
2. 判断对象从一张激活曲线升级为最坏rank、关键阶段和具体分配请求。若初始化或保存尚未覆盖，结果直接列出这项边界。
3. 点击首个失败点应回答：什么对象要申请多大空间，哪些对象仍驻留，为什么没释放，改变哪个局部策略能改变这一峰值。
4. 候选比较保持模型、有效训练目标、硬件和输入一致，允许后端采用各自合法策略；容量先筛选，再比较计算与搬运代价。第一层逻辑进度不能用来比较实际步时或MFU。
5. “免跑”指当前候选评估不依赖启动本次大规模训练，不排斥离线历史校准与独立验证。未获得足够证据时输出缺口或范围，不展示无条件的“精确预测”。

原始依据：[1113训练开发部交流诉求](../mindstudio-2027/planning/1113-训练开发部交流诉求.md)第1、2项及后续用户原声。第一层是解释和算账能力的交付；第二层以上内容为接入规划，尚未实现。
